# geist Benchmarks — AMD x86-64 (AVX-512)

geist's native `cpu_x86` backend (AVX-512 / VNNI, runtime-dispatched via `hw_probe`)
vs llama.cpp and Microsoft's bitnet.cpp, on the reference desktop.

- **Machine:** AMD Ryzen 9 9950X (Zen 5, 16C/32T, DDR5-6400), Linux.
- **Threads:** `OMP_NUM_THREADS=16 OMP_WAIT_POLICY=active`, same GGUF for both engines.
- **Baselines:** llama.cpp `b9827` (CPU backend, built from master) · bitnet.cpp =
  [microsoft/BitNet](https://github.com/microsoft/BitNet) `master` (its bundled
  llama.cpp fork). See [`compare_ternary_pi5.sh`](../compare_ternary_pi5.sh) for the
  pinned reference-build harness (`LLAMA_REF` / `BITNET_REF`).

geist matches-to-beats llama.cpp on x86 across both models and both phases.

## Ternary BitNet vs bitnet.cpp

BitNet b1.58 2B-4T (`i2_s`), biased-u8 VPDPBUSD ternary GEMV/GEMM + an i8 spec-head
for the F16 tied lm_head:

| metric | geist | bitnet.cpp | result |
| :-- | --: | --: | :-- |
| prefill pp128 | **1098** | 679.9 | **+61 %** |
| decode  tg128 | **103.1** | 54.3 | **+90 %** |

(Both engines re-measured 2026-07-13 on the same host/model after #102 +
#104; bitnet.cpp via its bundled `llama-bench -p 128 -n 128 -t 16`.) The
AVX-512 code path is bit-identical to the scalar oracle (Δ=0); the spec-head
greedy output is byte-identical to the exact F16 dense head; the t5 decode
output is byte-identical to the x4 decode.

### #102 optimization ledger (9950X, 16T `OMP_WAIT_POLICY=active`, mean-of-5)

| change | prefill pp128 | decode tg128 |
| :-- | --: | --: |
| baseline (main @e950433, re-measured) | 1036.7 | 91.7 |
| THP on >2 MB heap blobs (weight repacks, sketch) | 1044.7 | 92.9 |
| `GEIST_I2S_PAIR` default ON (q+k / gate+up fused decode) | — | 94.6 |
| `prefetchnta` on the x4 decode weight stream (512 B ahead) | — | +2.7 % (A/B 94.5 vs 92.0) |
| prefill token tile `I2S_X4_TT` 2 → 4 | 1093 | 94.9 |
| **#104**: t5 base-3 decode packing, 1.6 bpw (pow3 unpack, 5 trits/byte) | **1098** | **103.1** (+10.5 % A/B vs x4 93.3) |

The t5 blob rides in the same aux allocation after the x4 blob (prefill keeps
the x4 GEMM — compute-bound, the pow3 unpack would cost it): RSS 2464 →
2864 MB (+0.2 B/wt). `GEIST_I2S_T5=0` restores the pure 2-bit decode. The
Phase-A spike (`bench_t5_unpack`) that gated this: 362 vs 298 Gwt/s on a
DRAM-resident synthetic stream (ratio 1.21, gate ≥ 1.05).

Thread sweep: 16 T (physical cores) optimal for both phases; SMT (32 T) costs
−24 % decode. Measured **dead ends** (kept out, see #102): spec-head for top-k
sampling (stride-4 sketch rank noise beyond rank 1 is enormous — true top-40
rows ranked outside even top-8192 rough candidates; exact recall needs a
full-width phase 1 = the Q8 dense head's bytes), ReLU² block-skip in down_proj
(58 % element sparsity but **0.00 %** all-zero 64-element blocks — zeros never
cluster), `I2S_X4_TT=8` (register spills, 811 t/s).

From #212 (measured 2026-08-23, same host/protocol, mean-of-5): `I2S_JT`
sweep in the packed prefill GEMM — 4 confirmed optimal (2 → 1053, **4 →
1078**, 6 → 1057, 8 → 1035 pp128 t/s; 8 spills like `I2S_X4_TT=8` did).
AVX2-vectorizing `quantize_act_row` (byte-identical rounding via
trunc(q+copysign(.5,q)) + saturating packs, all i2s unit tests Δ=0): decode
unchanged within noise across two A/B rounds (119.6/119.7 base vs 120.2/119.3
vec) — the per-GEMV O(n_in) quant is invisible next to the O(n_in·n_out)
weight stream; reverted, decode stays bandwidth-bound.

CCD-aware thread distribution (measured 2026-09-01, `taskset`/`GOMP_CPU_AFFINITY`
experiment, no code change — the hypothesis from `n_l3_domains` in
[hw_probe.c](../../src/base/hw_probe.c#L187)): the 9950X's 2 CCDs are 8
physical cores each (`cpu0-7`/`cpu16-23` = CCD0, `cpu8-15`/`cpu24-31` = CCD1,
by `cache/index3/shared_cpu_list`). Two variants of "keep a token in one L3
domain" tested against the 16 T baseline (mean-of-5, pp128/tg128):

| config | prefill | decode |
| :-- | --: | --: |
| baseline, 16 T, no affinity (r1/r2) | 1060.6 / 1065.6 | 120.9 / 119.9 |
| 16 T, explicit stable CCD-ordered affinity (`GOMP_CPU_AFFINITY=0-15`) | 1041.9 | 120.1 |
| 8 T pinned to CCD0 only (`taskset -c 0-7`) | 916.7 | 105.4 |
| 8 T pinned to CCD1 only (`taskset -c 8-15`) | 932.1 | 109.8 |

Restricting either phase to one CCD costs 13–15 % on both prefill and decode
— losing half the cores outweighs any L3-locality gain, the DRAM controller
in the IOD is shared regardless of which CCD issues the request. Explicit
stable thread-to-core pinning at the full 16 T (no restriction, just a fixed
CCD-ordered mapping instead of default OS scheduling) lands inside the
±1.5 % noise band of the unpinned baseline — nothing to gain from static
placement on an otherwise-idle host either. `n_l3_domains` stays unconsumed;
no CCD-aware threading code added.

First-touch placement of the x4/t5 decode blobs (2026-09-01, analysis, no
code change): both `i2s_to_x4` and `i2s_to_t5`
([kernel_i2s.c:277,399](../../src/backends/cpu_x86/kernel_i2s.c#L277)) already
repack under `omp parallel for schedule(static)` over the same `n_groups`/
`n_out` extent the decode GEMVs (`i2s_x4_gemv_m1_avx512_vnni` et al.) later
consume with the identical `schedule(static)` — thread T's repack chunk is
thread T's decode chunk by construction, no separate placement pass needed.
`numactl --hardware` also reports **one NUMA node** on this host (single IOD
serving both CCDs), so first-touch placement — which only matters when a
thread's local DRAM channel differs from another's — has no lever to pull
here regardless. Confirmed structurally rather than by A/B: forcing the
repack to `num_threads(1)` and re-measuring decode was attempted but the run
coincided with unrelated host load (a concurrent build on this shared
machine drove `taskset`-free decode below 30 tg128, an order of magnitude
off baseline) and was discarded rather than reported as a result.

lm_head Q8-rescoring for spec_head finalists (2026-09-01, measured via
`GEIST_PROFILE_FORWARD=1`, no code change): the existing Q8 lm_head blob
(`f16_to_q8w`/`q8w_gemv_m1`, [kernel_f16_gemv.h:27](../../src/backends/cpu_x86/kernel_f16_gemv.h#L27))
already backs the *dense* fallback head, but `spec_head.c`'s phase-3 finalist
rescoring deliberately reads the exact F16 weight instead
([spec_head.c:790](../../src/archs/transformer/forward/spec_head.c#L790)):
"the Q8 case [is] int8-approximate, so bit-identity to it is neither
achievable nor desirable" for the argmax-sensitive finalist set. Cost profile
on the reference host (`bench_perf_sweep --repeats 1`, pp128/tg128,
BitNet 2B-4T): `lm_head` totals 1.55 ms/token (207.8 ms / 134 calls) against
~7.9 ms/token transformer body, i.e. ~16 % of forward time — not negligible.
But BitNet's finalist count defaults to `SPEC_TOPK=1024`
([spec_head.c:125](../../src/archs/transformer/forward/spec_head.c#L125)),
5.2 MB against the sketch's fixed 82 MB (~6 % of the head's own read).
Halving just that 6 % slice bounds the best-case win at **~0.5 % of total
decode time** — under the ±1.5 % noise floor established above — while
trading away a documented correctness margin on the exact step that decides
which candidate wins a near-tie. Not implemented: the ceiling is
unmeasurable and the code already argues against it.

## Reference sanity bar: ik_llama.cpp IQ2_BN

Not a geist comparison — a plausibility check that this host measures ternary
inference in the ballpark the wider ecosystem reports, per #212's request for
an independent sanity bar. [ikawrakow/ik_llama.cpp](https://github.com/ikawrakow/ik_llama.cpp)
`3c58ae3` (2026-09-01), built `-DGGML_NATIVE=ON` (picks up this host's
AVX-512/VNNI). Model: [1bitLLM/bitnet_b1_58-3B](https://huggingface.co/1bitLLM/bitnet_b1_58-3B)
(3.43 B params) converted to F16 GGUF then quantized `iq2_bn`
(876.96 MB) via `llama-quantize`, no imatrix. `llama-bench -t 16 -r 5`:

| test | this host (9950X) | [ik_llama.cpp wiki, 7950X, 2024-07](https://github.com/ikawrakow/ik_llama.cpp/wiki/July-2024:-BitNet-performance-comparison) |
| :-- | --: | --: |
| pp512 | 362.45 ± 6.97 | 540.82 ± 2.48 |
| pp128 | 507.07 ± 13.12 | not reported |
| tg128 | 71.70 ± 0.66 (73.02 ± 0.08 at pp128) | 53.46 ± 0.07 |

Decode lands 34–37 % above the 2024 7950X figure, consistent with a newer
core + faster DDR5 memory. Prefill is the surprise: pp512 is 33 % *below*
the 7950X number, while pp128 on the same binary/model is 40 % *above* pp512
— a real, low-variance (±1.3–1.9 %) batch-size-dependent effect in
ik_llama.cpp's own `iqk` GEMM kernel selection, not host noise, and not
something this ticket investigates further (out of scope: it's ik_llama.cpp's
kernel, not geist's). Different model (3.43 B vs BitNet 2B-4T), different
quant (`iq2_bn` vs geist's `i2_s`/t5), different CPU generation and a
different ik_llama.cpp commit than the 2024 wiki page — this is a ballpark
check, not a ranked comparison, per #364's rule to compare engine ratios only
within one hardware/backend cell.

## The generic linear's prefill dots (2026-10-01)

The dtypes without a native x86 kernel (Q4_0, Q4_1, Q3_K, Q5_K, the IQ
formats, TQ2_0, BF16, F16 prefill) go through `linear_generic.c`: dequantize
a weight row into L1, dot it in fp32. For M>1 it dotted each row against one
token at a time, two loads per FMA, and the load ports held it at 0.055 ns
per FMA on one thread whether the data sat in L1 or L2. It takes 4 rows
against 3 tokens now, 12 accumulators and 7 loads per 12 FMAs: 0.035 ns in
L1, 0.039 ns from L2. Same host as the ledger above, 4 threads:

| one call | before | after |
| :-- | --: | --: |
| Q4_0, 4096 × 4096, 64 tokens | 17.3 ms | 12.4 ms |
| F16, 4096 × 4096, 64 tokens | 15.8 ms | 10.9 ms |
| BF16, 48 × 5120, 64 tokens | 227 µs | 153 µs |
| Q4_0, 4096 × 4096, 8 tokens | 3.82 ms | 3.36 ms |

End to end, Llama 3.2 1B's geometry with a Q4_0 body
(`tools/gen_synth_gguf.py --preset llama32-1b-q4_k --wtype q4_0`), both
builds from scratch, 10 cycles with a control:

| | before | after | change |
| :-- | --: | --: | --: |
| prefill, 64 tokens | 1305 ms | 782 ms | −39.2 % [−42.7, −36.2], 10/10 |
| prefill, 256 tokens | 5163 ms | 3114 ms | −39.3 % [−43.0, −36.6], 10/10 |
| decode | | | noise |

## Reproduce

```bash
# geist (native cpu_x86 backend — the x86 default since #108):
make TARGET=linux
OMP_NUM_THREADS=16 OMP_WAIT_POLICY=active \
  bin/linux/release/tests/bench_perf_sweep --gguf $M --seq-lens 128 --decode-n 128

# llama.cpp / bitnet.cpp reference (same GGUF, 16 threads):
llama-bench -m $M -p 128 -n 128 -t 16
```

These numbers feed the headline scoreboard — see [`headline_results.json`](../headline_results.json)
(AMD 9950X rows) and [`../README.md`](../README.md).
